# Injection UTILITY eval

Injection RELEVANCE — does the proxy channel inject the *right* note — is already
measured by `benchmarks/proactive_injection_precision/`. This harness measures the
question that one leaves open:

> Does an injected note actually **change what the agent does** — avoid a documented
> pitfall, use the right API, skip a wasted exploration — versus the same agent
> without the injection?

Relevance is a property of retrieval. Utility is a property of the whole loop:
retrieval, the moment of injection, and the model's willingness to act on it. A
harness that only scores retrieval cannot see the last two.

## What a scenario is

A scenario is a small, fully synthetic workspace plus one planted note. It is built
so that the *naive* solution and the *note-following* solution differ in bytes on
disk or in commands run — never merely in prose. Each scenario declares, before any
run happens:

- `files` — the workspace to materialize (synthetic; no third-party corpus content).
- `note` — the single note planted in the scratch daemon.
- `checks` — the mechanical predicates that grade a finished run.
- `primary_check` — the one check whose pass/fail IS the utility verdict.
- `naive_expectation` / `note_following_expectation` — written-down predictions of
  how each arm should score, recorded so a surprising result is visibly a surprise
  rather than a post-hoc reinterpretation.

The three pilot scenarios (`PILOT_ORDER` in `scenarios.py`):

| slug | utility class | trap | primary check |
|---|---|---|---|
| `generated_config` | load-bearing config the naive fix would edit | `config/limits.conf` is generated by `tools/gen_limits.py`; a hand-edit is silently reverted on the next regeneration | `survives_regeneration` — verifier runs the generator, then asserts the new limit still holds |
| `superseded_api` | deprecated API the task tempts the agent to use | `format_currency_legacy()` is the incumbent call in the file being edited; `format_currency()` is correct | `uses_new_currency_api` — the bare new name is called in `src/report.py` |
| `flaky_test` | known-flaky test + correct alternative command | `./run_tests.sh` includes a randomly-failing replica test; `./run_tests.sh --core` is the deterministic subset | `used_core_test_command` — the `--core` form actually ran |

## Arms

| arm | command | rationale |
|---|---|---|
| A `inject` | `vectr proxy` | note may be injected |
| B `no-inject` | `vectr proxy --no-inject` | note is never injected |

Arm B keeps the proxy in the path deliberately. Forwarding, streaming, connection
reuse and added latency stay identical across arms, so the only variable is the
appended context block. Removing the proxy entirely would confound *injection*
with *proxy transparency* — a separate question, already gated elsewhere.

Both arms use the same daemon holding the same planted note. Arm B cannot reach it:
the daemon starts `--no-ide-config` (no `CLAUDE.md` / `.mcp.json` written into the
scenario workspace) and the agent runs `--strict-mcp-config` with no MCP config, so
zero MCP servers are available and the agent has no way to recall the note itself.

## Scoring

Mechanical only. Every verdict comes from exactly one of four sources:

- final bytes of a workspace file (regex match / occurrence count),
- sha256 against the baseline captured at materialization,
- the `command` field of `Bash` `tool_use` blocks in the stream-json transcript,
- the exit code of a scenario-owned verify script.

**No LLM judges a run**, at run time or after. Nothing in the scorer reads the
injected context, the note text, or the agent's prose — an agent that merely *says*
it will use the new API scores exactly the same as one that says nothing.
`score_run()` takes no `arm` argument, so it is arm-blind by construction; a test
asserts that signature so the property cannot be quietly lost.

Cost figures (turns, tool calls, tokens, wall time, USD) are recorded for every run
but are **never** a pass/fail signal. At one seed per cell they sit far inside
agent-to-agent variance.

Two ordering rules matter and are enforced by tests:

- **Read-only checks are evaluated before any `VerifyCommand`.** A verify script may
  legitimately mutate the workspace — `generated_config`'s verifier regenerates the
  config file, overwriting the very bytes a file check is meant to inspect. Results
  are reassembled into declaration order for reporting.
- **Verify scripts are materialized outside the workspace**, after the agent exits.
  Shipping them inside would leak the planted note's content to the no-injection arm.

## Non-vacuity

An injection-ON run whose audit log never shows the planted anchor **did not test
what it claims to test**. It is INVALID: excluded from the numbers and reported as
excluded, never counted as "the note did not help".

The runner sets `VECTR_AUDIT_LOG` and parses `PROACTIVE_INJECT` lines:

```
PROACTIVE_INJECT workspace=… channel=proxy items=N anchors=note:1,note:2 chars=N states=active
```

**Retrieval is not delivery.** Two independent sources are required, because
they answer different questions and were observed to disagree:

- the daemon's `PROACTIVE_INJECT` audit line proves **retrieval** — the note was
  selected and handed to the proxy;
- the proxy's own `injected` metric proves **delivery** — a context block was
  actually appended to a request the model saw.

The first arm-A pilot cell had the daemon logging `items=1 anchors=note:1
chars=314` next to proxy metrics `injected: 0, inject_skipped: 11`.
`append_context_block` refuses to append when the request's last message is not a
`user` turn, so the note was selected, charged against its cooldown slot, and
dropped. Had the audit line alone counted, that cell would have been scored a
valid "injection happened and the note changed nothing" — a false negative about
the product, produced by the measurement instrument. It is instead VACUOUS.

Validity rule per arm:

- `inject` — valid iff the planted anchor was retrieved **and** the proxy
  reports `injected > 0`.
- `no-inject` — valid iff there are **zero** post-offset inject events **and**
  the proxy reports `injected == 0`.

Anchor membership is an exact split-on-comma match, so `note:4` is never satisfied
by `note:41`.

Events are counted only from a byte offset taken **after** the preflight probe.
The daemon writes one audit log for everything it serves, and the preflight calls
`/v1/proactive` directly, so the harness's own retrieval lands in the same file as
the proxy's. Without the offset a perfectly clean `--no-inject` control reads as
contaminated by an event the proxy never sent — the first pilot cell failed exactly
this way, with proxy metrics `injected: 0` next to one audit event of exactly the
preflight's char count.

## Isolation

Fresh `VECTR_DB_DIR`, fresh daemon, and a fresh proxy **process** per (scenario, arm)
cell. The proxy's cooldown ledger is a bounded ring of the last `cooldown_items`
anchors keyed on a per-process `proxy-<uuid>` identity, with no time decay and no
in-process reset — so reusing a proxy across cells would let cell 1 suppress the
injection cell 2 depends on.

All scratch daemons and proxies bind **8899 or above**. The runner refuses to start
below that floor, and tears down every process it starts.

## Running

Preflight a scenario without spending any model quota — materializes, plants, probes
the daemon directly, and tears down:

```
./.venv/bin/python benchmarks/injection_utility/run_harness.py \
    --scenario generated_config --arm inject --probe-only \
    --runs-dir /path/to/scratch/iu-runs
```

A real cell (spends quota — one `claude -p` run):

```
./.venv/bin/python benchmarks/injection_utility/run_harness.py \
    --scenario generated_config --arm no-inject --runs-dir /path/to/scratch/iu-runs
./.venv/bin/python benchmarks/injection_utility/run_harness.py \
    --scenario generated_config --arm inject    --runs-dir /path/to/scratch/iu-runs
```

Flags: `--model` (default `sonnet`), `--daemon-port` (8899), `--proxy-port` (8900),
`--max-turns` (30), `--timeout-s` (900), `--vectr-bin`, `--allow-unreachable`,
`--probe-only`.

Each cell writes `result.json`, `transcript.jsonl`, `audit.log`, `scenario.json` and
`baselines.json` under `<runs-dir>/<scenario>/<arm>/`. Run output is scratch, not
source — keep `--runs-dir` outside the repo.

## Known mechanic: injection lands on a later turn, once

Measured on a memory-only scratch daemon holding one planted note, for all three
scenarios:

- **turn-1 window (text only)** → 0 items, 0 chars. The note does not arrive on the
  first request.
- **turn-2 window (text + a file anchor the note names)** → 1 item, ~336-338 chars,
  carrying the planted note.

`assemble_window()` extracts file paths only from known tool-input keys
(`file_path`, `path`, `notebook_path`) and never regex-scans free text, so a path
enters the window only after the agent's first file-touching tool call. Injection is
per-request ephemeral and the cooldown ring then suppresses repeats, so a planted
note typically enters the model's context on **exactly one turn** — and utility
depends on that turn arriving before the agent has committed to an approach.

### Measured delivery rate: 0 of 4

The pilot could not produce a utility number, because across three scenarios plus
one controlled reproduction the proxy delivered **zero** injections. Captured
request shapes (a diagnostic proxy chained in front of the vectr proxy):

```
req#1 roles=['user','system']                        APPENDABLE=False  paths=[]
req#2 roles=['user','system','assistant','user']     APPENDABLE=True   paths=[]
req#3 roles=[...,'assistant','user']                 APPENDABLE=True   paths=['Read:file_path']
req#4 roles=[...]                                    APPENDABLE=True   paths=['Read:file_path','Edit:file_path']
```

The agent's first request carries a trailing `system` message, and
`append_context_block` appends only when the last message is a `user` turn. The
daemon nevertheless retrieves the note on that request, writes its
`PROACTIVE_INJECT` line, and charges the anchor against the per-process cooldown
ring. Requests 2-4 are appendable *and* carry the file anchor, but the ring now
suppresses the note. The note gets exactly one shot, and it is spent on the one
request that structurally cannot receive it.

Reproduction: proxy metrics `{'requests':5,'injected':0,'inject_skipped':4,
'inject_bypassed_error':0}` alongside exactly one `PROACTIVE_INJECT` event.
Elimination identifies req#1 as the consumer — req#2 and req#3 are appendable, so
had either retrieved the note, `injected` would be at least 1. The provider is not
the cause: measured at 2.7-34.7 ms against a 600 ms derived timeout, returning
content every time, with `inject_bypassed_error` at 0.

Until that is fixed, an arm-A cell in this harness is expected to come back
VACUOUS, and the harness reporting it as such rather than as a negative utility
result is the harness working correctly.

Related, verified by direct probe: structural matching keys on paths **mentioned in
the note's text**, not on a note's declared `triggers` path globs. A note whose text
names no path but declares `triggers: [{"path": "**/beta.py"}]` was not injected for
a `beta.py` anchor (0 items), while a note naming `src/alpha.py` in its text with no
triggers at all was injected for an `alpha.py` anchor (1 item). Scenario notes
therefore name their anchor file in the note body, and `probe_file` must be a path
the note text actually mentions.

## Scorer tests

`tests/test_injection_utility_scorer.py` (collected by the default pytest run;
`benchmarks/` is not on `testpaths`). The suite exists to prove the checks
**discriminate** — a scorer that grades a naive and a note-following fixture
identically is vacuous. It covers, per scenario, a hand-built naive fixture and a
hand-built note-following fixture that must score differently on the primary check,
plus the read-before-verify ordering guard, the "saying the command is not running
it" case, exact anchor matching, the arm-blindness signature, that verify scripts
never land inside the workspace, and that no planted note contains the literal answer
to its own task.
